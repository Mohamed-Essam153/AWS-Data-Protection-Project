## Secrets Manager or Parameter Store?

| Secrets Manager | Parameter Store |
|---|---|
| credentials that need rotating | configuration |
| built-in rotation, RDS integration | SecureString but no built-in rotation |
| cross-account sharing | standard tier is free |
| ~$0.40 per secret per month | |

## Rotation, the four steps

A rotation Lambda for the third-party key would follow the standard Secrets Manager flow:

1. `createSecret`: generate a new key and store it as `AWSPENDING`.
2. `setSecret`: register it with the third party.
3. `testSecret`: call the third party with `AWSPENDING`.
4. `finishSecret`: move `AWSCURRENT` to the new version; the old one becomes `AWSPREVIOUS`.

Our fake partner has no API to register keys with, so step 2 has nothing to call. T18 does the part we can prove: it writes a new value and checks that `AWSCURRENT` moved and the old version is kept as `AWSPREVIOUS`, without printing either value.

```bash
aws secretsmanager list-secret-version-ids --secret-id dp-lab/thirdparty/api-key \
  --query 'Versions[].{Version:VersionId,Stages:VersionStages}'
```

## Rules

- The app fetches secrets at runtime and caches them for the life of the execution environment, so a rotation is picked up without a redeploy.
- No secret in code, environment variables, logs, screenshots or the repo. The Lambda's environment only holds the secret's ARN and the parameter's name.
- Never screenshot `get-secret-value`.
- A failed rotation would go to `dp-lab-security-alerts` through EventBridge, to the secret's owner.
